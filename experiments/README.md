# Эксперименты и результаты запусков

## Запись реального запуска

Из корня DID_hack на Python 3.12+:

```sh
python3 experiments/results.py add
```

Ответьте на вопросы. Enter оставляет неизвестное значение как JSON null.
Идентификатор можно взять из запуска робота; если его нет, инструмент создаёт UUID.
Для результата цели: yes — достигнута, no — не достигнута, unknown/Enter — неизвестно.
По умолчанию данные сохраняются в `experiments/results/runs.json`.
Не вносите туда выдуманные результаты.

Можно передать известные поля через параметры `add`: `--run-id`, `--scenario`,
`--seed`, `--mode`, `--initial-position X Y`, `--goal X Y`, `--success yes|no|unknown`,
`--duration-s`, `--error`, `--energy-used`, `--collected`, `--delivered`.
При передаче хотя бы одного поля остальные остаются null. Добавьте `--interactive`,
если хотите ответить на вопросы об оставшихся полях. Seed 0 и измеренный расход 0
сохраняются как настоящие нули; отсутствие измерения остаётся null.

Координаты — метры в существующей системе map. Длительность — секунды между
началом и завершением проверяемой задачи: используйте одну и ту же шкалу времени
и границы задачи во всех сравниваемых прогонах. Не смешивайте симуляционное время
с временем настенных часов. `recorded_at` — время сохранения записи в UTC,
а не время начала миссии. Энергия — существующие единицы батареи на том же участке.

Успешность здесь означает достижение заданной цели, а не автоматически finish
миссии, сбор или доставку образцов. Записывайте её по наблюдению или подтверждению
исполнителя. Если цель ещё не проверена, сохраняйте unknown. Описание ошибки
может быть неизвестно даже при подтверждённой неудаче. collected/delivered
заполняйте только при наличии фактических данных; delivered не выше collected,
если известны оба значения.

## Сводка

```sh
python3 experiments/results.py summary
```

Вывод — JSON: число записей, успешных, неудачных и с неизвестным исходом,
доля успешных среди запусков с известным исходом (число от 0 до 1), средняя,
минимальная и максимальная длительность успешных запусков. Для длительности
указаны число доступных и число отсутствующих измерений. Неизвестные исходы
не считаются неудачами, неизвестные длительности не считаются нулями.
Отдельный массив failures содержит записи подтверждённых неудач и их ошибки.
Без известных исходов или длительностей соответствующие показатели равны null.
Общая сводка объединяет режимы и сценарии, это не доказательство эффекта адаптации.

## Отдельные тестовые данные

Следующий пример содержит только искусственные значения:

```sh
python3 experiments/results.py --test-data add --run-id test-demo-ok --scenario easy --seed 1 --mode adaptive --initial-position 0 0 --goal 2 1 --success yes --duration-s 8
python3 experiments/results.py --test-data add --run-id test-demo-fail --success no --error "TEST: препятствие"
python3 experiments/results.py --test-data summary
```

Тестовый файл — `experiments/test_data/runs.json`. У каждого файла есть метка
dataset_kind: real или test. Инструмент отказывается читать или дописывать файл
в другом режиме, чтобы тестовые результаты не попали в реальную сводку.

Свой путь задаётся до подкоманды: `--file /путь/к/runs.json`. Для тестов обязательно
добавляйте `--test-data`. Повторный run_id отклоняется, существующая запись не меняется.
Повреждённый файл не перезаписывается. Сохранение атомарное; запускайте только
один процесс записи на файл одновременно. Сводка отсутствующего файла показывает
пустой набор и не создаёт файл.

## Источники и ограничения

DID LAB предоставляет MissionControl, `/api/state` и WebSocket-телеметрию.
`scripts/web_check.py` сохраняет receipts физического Gazebo-прогона отдельно
в `experiments/runs/docker`. `results.py` остаётся ручным регистратором;
source его записей — manual. Даже MissionState сам по себе не содержит всех
нужных данных: например,
начальную позицию, длительность и подтверждение достижения произвольной цели
нужно получать отдельно. Регистрируйте только наблюдавшиеся значения;
real означает фактический запуск выбранного стенда, а не физическое оборудование.
При регистрации Gazebo укажите источник в error/сопроводительном receipt.
Кинематика и демонстрационные данные идут только в набор `--test-data`.

Для проверки инструмента на временных тестовых файлах:

```sh
python3 -m unittest discover -s tests -p test_results.py -v
```

Тесты удаляют свои временные данные и не записывают результаты в реальные файлы.
