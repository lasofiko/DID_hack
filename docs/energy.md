# Энергия движения и поворотов: подключение для Искандера

## Что реализовано

`did_ml.energy.EnergyModel` хранит две независимые оценки для каждого центра
клетки в map:

- движение: `energy_per_m`, единицы энергии/метр;
- поворот на месте: `energy_per_rad`, единицы энергии/радиан.

Для поворотов есть отдельная сущность `TurnEnergyModel`, доступная также через
`model.turns`. У обоих компонентов свои измерения, статистика и неопределённость.
В проверенной версии MissionControl ещё не реализован. Подключение к ROS и
проверка реального расхода остаются работой интеграции, а не готовым результатом.

## Изменения контракта

Старые прямые `EnergyMeasurement` и `CostEstimate` по-прежнему работают.
В EnergyMeasurement добавлено необязательное поле `angle_rad`. Для turning=True
оно обязательно при обработке, иначе замер пропускается. `estimate()` возвращает
прежний CostEstimate только для движения.

Добавлены `TurnEnergyMeasurement` и `TurnCostEstimate`, методы `update_turn`,
`estimate_turn`, `estimate_energy` в контракт EnergyModel и отдельный контракт
TurnEnergyModel. Будущие реализации EnergyModel должны реализовать эти методы.
HTTP/WS, Observation и координаты не изменены. Изменение требуется учесть
Искандеру при написании адаптера: старого флага turning недостаточно для угла.

## Создание и использование

Ниже только демонстрационные значения, не параметры настоящего робота:

```python
import math
from did_ml.energy import EnergyModel

cell = {"x": 0.5, "y": 0.5}  # Центр клетки существующей карты.
model = EnergyModel(initial_energy_per_m=3.0)
model.update({
    "cell": cell, "distance_m": 0.2, "energy_used": 0.4, "turning": False,
})
model.update({
    "cell": cell, "distance_m": 0.0, "energy_used": math.pi,
    "turning": True, "angle_rad": math.pi / 2,
})
print(model.estimate(cell))       # energy_per_m=2, uncertainty=None
print(model.estimate_turn(cell))  # energy_per_rad=2, uncertainty=None
print(model.estimate_energy(cell, distance_m=1, angle_rad=0))  # Только проезд: 2.
print(model.estimate_energy(cell, distance_m=0, angle_rad=math.pi/2))
# Только поворот на 90 градусов: pi единиц энергии.
```

Поворот можно передать отдельно через `update_turn` с полями cell, distance_m,
angle_rad, energy_used (без turning). Не вызывайте update и update_turn для
одного и того же замера: это удвоит его вес в статистике.

`initial_energy_per_m` обязателен и берётся из конфигурации/калибровки команды.
`initial_energy_per_rad` необязателен: по умолчанию None, то есть расход поворота
ещё неизвестен. Без замеров/настройки прогноз с ненулевым углом возвращает None,
а не считает поворот бесплатным. Прогноз без поворотов работает независимо.
Для неизвестной клетки используется начальная оценка, не оценка соседей.

Настройки надёжности: `min_distance_m`, `max_energy_per_m`, `min_angle_rad`,
`max_energy_per_rad`. Минимумы по умолчанию 0, максимумы отсутствуют. Настройте
их по точности и ограничениям датчиков, не выдумывайте физические пороги.
При обучении длина прямого участка или угол чистого поворота должны быть >0.

## Реальные измерения и угол

Адаптер робота передаёт расстояние и энергию за один согласованный временной
интервал. Энергия — battery в начале минус battery в конце, в существующих
единицах батареи. Длина — фактически пройденный путь, не запланированная длина.
Проверьте свежесть и согласованность показаний; зарядка, сброс батареи или
пропуск данных не должны становиться выдуманным нулевым замером.

Угол измеряется в радианах: 90 градусов = pi/2. Используйте ориентацию из
доступной одометрии/TF и сумму абсолютных приращений yaw за интервал, а не
разность только начального и конечного направлений. Например, +90 и −90
дают pi радиан суммарного поворота, а не 0. Несколько оборотов могут дать >2*pi.

При достаточно частых показаниях для каждого шага нормализуйте разность yaw
через `atan2(sin(delta), cos(delta))`, затем суммируйте модуль. Это корректно
проходит границу −pi/pi. Если между показаниями возможен поворот больше pi,
его нельзя восстановить этим способом: нужна более частая/развёрнутая
ориентация. Не используйте сумму подписанных углов для расхода энергии.
Поле angle_rad принимает уже рассчитанную неотрицательную сумму.

## Разделение действий и клеток

Выбранная логика робота: поворот на месте, затем прямой проезд. Одновременно
поступательное движение и поворот запрещены. Контроллер должен обнулить
линейную скорость при повороте и угловую при прямом проезде; для коррекции
направления сначала остановиться. Подробное правило: docs/team.md.
Ограничение пока не подключено к роботу: контроллер ещё не реализован.

Для обучения движения: turning=False, distance_m>0, angle_rad отсутствует либо 0.
Для обучения поворота: turning=True, distance_m=0, angle_rad>0. Один чистый
поворот целиком в одной клетке. Остановка без движения/поворота не обучает модель.

Одновременное движение и поворот отбрасываются обоими компонентами: один общий
расход не позволяет определить отдельно коэффициенты метра и радиана.
Не отправляйте общий расход одновременно в оба компонента и не вычитайте
предполагаемый расход движения, выдавая остаток за измеренный поворот.
Для калибровки используйте прямые участки и отдельные повороты на месте.

По умолчанию критерий строгий: любой ненулевой distance_m при повороте или
angle_rad при прямом движении делает замер смешанным. Для известного шума
датчиков можно настроить `max_turn_distance_m` и `max_straight_angle_rad` в
конструкторе EnergyModel. Оба по умолчанию равны 0. Это только допуски измерений,
не разрешение ехать по дуге. Значения должны обосновываться точностью датчиков;
не замалчивайте реальное движение произвольно большим допуском. При повороте
distance_m в пределах допуска игнорируется, при прямом проезде angle_rad в
пределах допуска игнорируется. Исходные данные при этом не переписываются.

Движение через границы клеток разделяйте до update, с измеренной энергией
каждой части. Суммарную энергию нельзя произвольно распределять между клетками.
Модель не знает размер сетки; estimate и estimate_turn получают точный центр
той же клетки в map. Координаты центра вычисляйте одинаково, без произвольного
округления. В контракте нет времени/концов отрезка; модель не проверяет их сама.

## Прогноз энергии

Для одного действия в одной клетке выбирается одна формула:

- Прямое движение: `E = energy_per_m * distance_m`, angle_rad=0.
- Поворот на месте: `E = energy_per_rad * angle_rad`, distance_m=0.

`estimate_energy(cell, distance_m, angle_rad)` выбирает соответствующий случай,
без сложения компонентов. Если расстояние и угол одновременно >0, возвращается
ошибка ValueError. При обоих нулях прогноз равен 0: это отсутствие движения,
а не оценка расхода ожидания. Для поворота с неизвестной стоимостью возвращается
None — не подменять его нулём. Некорректные координаты/числа и переполнение
также дают ValueError. До вызова должна быть известна длина конкретного проезда
либо угол конкретного поворота. Если команда ещё не определена или робот
вращается без заданного конечного угла, полного прогноза нет: не подставляйте
выдуманный угол или число будущих поворотов. Сохраняйте только фактические замеры.
Модуль не предсказывает последовательность действий или общий расход маршрута.

Это простая линейная гипотеза для одного заданного прямого проезда либо
поворота на месте, которую нужно проверить в вашей среде. Повороты на ходу в выбранной
логике не выполняются. Модель не учитывает скорость,
время ожидания, фиксированную цену старта или другие действия и не гарантирует
точный полный расход миссии. Настоящие правила расхода задаёт среда/ТЗ.

## Статистика и режимы

Для движения усредняются energy_used/distance_m; для поворота —
energy_used/angle_rad. Каждый принятый замер имеет одинаковый вес. uncertainty
в каждой оценке — выборочное стандартное отклонение коэффициента (n−1),
соответственно энергия/м или энергия/рад. До двух замеров оно None. Это не
стандартная ошибка среднего или неопределённость прогноза действия.

Неверные типы, NaN/Infinity, отрицательные значения, нулевой знаменатель,
нарушения настроенных пределов и численное переполнение/потеря ненулевого
коэффициента до нуля отбрасываются без изменения статистики.
update и update_turn возвращают None, отдельного признака принятия нет.
Для наблюдения за качеством данных доступны `model.diagnostics()` (движение)
и `model.turns.diagnostics()` (повороты). Каждый возвращает копию словаря с
accepted, rejected, last_rejection. Последняя причина сохраняется и после
следующего успешного замера. Повороты, направленные через update, учитываются
только в диагностике поворотов; неверный флаг turning — в диагностике движения.
Причины: invalid_measurement, invalid_turning_flag, mixed_motion,
distance_below_minimum, angle_below_minimum, rate_above_maximum, numerical_range.
Метод diagnostics — дополнение реализации, основной Protocol не изменён.
Статистических выбросов автоматически не удаляем: это может быть изменение среды.
Все замеры накапливаются, окно забывания и сохранение на диск не реализованы.

Один экземпляр модели живёт весь прогон; для независимого прогона создавайте
новый. В baseline агент сохраняет начальные стоимости обоих компонентов,
не обновляя используемую при планировании модель. В adaptive агент обновляет
обе оценки и решает, когда применять их и перепланировать путь. Модель не
управляет роботом. У обоих режимов должны быть одинаковые начальные настройки.

## Проверка

Из корня DID_hack:

```sh
python3 experiments/energy_demo.py
PYTHONPATH=packages/contracts:packages/ml python3 -m unittest discover -s tests -v
```

Пример явно помечен как искусственный, запускается без ROS и зависимостей сервера.
Показывает обе оценки, изменение неопределённости, сохранение baseline и отдельные
прогнозы движения и поворота. Он не записывает демонстрационные данные в реальные результаты.
