# EnergyModel Марии в DID LAB

Агент использует `did_ml.energy.EnergyModel` из PR #1 без изменения её алгоритма.
`did_ml.factory.make_energy_model(config)` создаёт новый экземпляр для каждой
миссии. ROS-пакет устанавливает `did_ml` вместе с агентом. В Compose установлен
`DID_ENERGY_FACTORY=did_ml.factory:create_energy_model`; внешний factory должен
реализовать `update`, `update_turn`, `estimate`, `estimate_turn`, `estimate_energy`.
Никакой LLM для работы этой интеграции не требуется.

## Измерения

`RobotState` сохраняет последовательность валидных `/odom` и `/did/battery`.
`EnergyObserver` суммирует фактические приращения пути и абсолютные приращения
`atan2(sin(delta_yaw), cos(delta_yaw))`. Измеряется весь угловой путь, включая
переход ±pi и смену направления, а не только разность конечных ориентаций.
Точки одометрии переводятся в map существующим `CoordinateTransform` ровно один раз.

Энергетическая сетка имеет шаг `energy_cell_size=0.5 м`, origin/yaw карты.
`cell` — точный центр плитки в map, не индекс OccupancyGrid. Измерение принимается
только если весь интервал находится в одной плитке. **Общий расход не делится
между несколькими клетками**. У пересечения границы отбрасывается интервал;
новый якорь начинается в новой клетке.

Прямой интервал передаётся один раз через `update`:

```python
{"cell": {"x": -1.25, "y": -0.25}, "distance_m": 0.10,
 "energy_used": 0.20, "turning": False, "angle_rad": 0.0}
```

Поворот передаётся только через `update_turn`:

```python
{"cell": {"x": -1.25, "y": -0.25}, "distance_m": 0.0,
 "energy_used": 0.006, "angle_rad": 0.20}
```

Числа примеров искусственные; они не результаты эксперимента. Реальный
`distance_m` поворота содержит измеренное смещение, а не принудительный ноль.
Смешанные интервалы отклоняются. Контроллер выдаёт либо linear, либо angular,
с нулевой командой между фазами и гистерезисом выравнивания направления; ROS-адаптер дополнительно запрещает смешанный
`TwistStamped`. Safety/watchdog сохраняет приоритет. При краткой потере свежести navigator
сразу публикует нули и ждёт валидные данные максимум 0.5 с. Движение
возобновляется только после повторного чтения всех датчиков и проверки safety.
Постоянная потеря, emergency, разряд и отмена остаются терминальными.
При возврате navigator завершает движение после достижения существующего
`base_tolerance=0.18 м`, с обязательной проверкой свежести и safety.
Обычные цели сохраняют `goal_tolerance=0.09 м`; радиус базы не разрешает
движение через препятствия и не обходит подтверждение сервиса finish.

Параметры адаптера в `AgentConfig`: выдержка после смены действия 0.20 с,
минимум пути 0.08 м, минимум угла 0.15 рад, максимум рассогласования часов 0.10 с,
пропуски odom >0.25 с / батареи >0.30 с отбрасываются. Допуски побочного
перемещения при повороте 0.01 м и угла прямого интервала 0.02 рад предназначены
для малых ошибок одометрии стенда. Это настройки MVP, **не официальная
калибровка датчиков**. Их пригодность для официального робота нужно измерить.
Коллинеарные точки A* объединяются в участки до примерно 0.30 м, сохраняя
повороты и точное прохождение промежуточных центров. Фактический отрезок
до цели каждый раз проверяется на карте; дрейф не оправдывает снятие safety.
Физический профиль `configs/agent.json` ограничен 0.12 м/с и 0.4 рад/с после
наблюдавшегося расхождения world/odom. Это снижение скорости, не исправление
локализации; запас clearance и пороги безопасности сохранены.

Скачки odom, сброс батареи, переполнение очереди, повторные stamps и невалидные
оценки не становятся обучающими измерениями. Якорь расходуется до вызова модели;
её диагностика подтверждает принятие, поэтому один интервал не учитывается дважды.

`Float32 /did/battery` не имеет исходного stamp: доступна отметка ROS-clock
получения. Согласование с odom приблизительное, не аппаратно синхронное.
Отбрасывание большого skew снижает риск, но не устраняет задержку DDS.
Неизвестную примесь затрат (например, hazard) нельзя выделить из одного скаляра.
При известном hazard/collision safety завершает движение до обучения.

## Baseline, adaptive и резерв

В обоих режимах модель учится и публикует наблюдения. Baseline сохраняет
исходные стоимости A*: `energy_per_m=3`, неизвестный поворот резервируется
`energy_per_rad=0.25`. Обучение не изменяет веса baseline.
Adaptive переносит оценки только непосредственно измеренной плитки в карту
планирования. A* учитывает направление прихода и цену следующего поворота;
обновление затрат вызывает остановку и перепланирование, включая возврат.
При исследовании сохраняется текущая цель; повторный расчёт пути не тратит
шаги поиска образцов. На одну цель допускаются до 20 таких повторов.
Движение в A* имеет нижнюю границу 1 для допустимой эвристики.

Мария хранит среднее всех принятых затрат, отдельную статистику движения и
поворота; uncertainty — выборочное стандартное отклонение, не доверительный
интервал среднего. Нет забывания старых данных: реакция на смену затрат
может быть медленной. Журнал отмечает расхождение нового измерения с оценкой,
но не объявляет скрытое изменение среды известным фактом.

Неизвестный поворот в модели остаётся `null`; планирование и резерв используют
консервативную ненулевую настройку. Возврат резервирует сумму движения и
поворотов, затем множитель 1.5 и 8 единиц батареи. Для движения сохраняется
максимальная общая наблюдённая ставка BatteryManager, даже если локальное
среднее ниже. Это консервативная оценка, не гарантия для неизвестного грунта.

## Публичные данные и проверка

`/did/agent/knowledge` и WebSocket содержат оценки `energy_per_m`, uncertainty,
`energy_per_rad`, turn_uncertainty, количества прямых/угловых замеров и
диагностику принятых/отклонённых интервалов. Журнал показывает фактические
`EnergyMeasurement`/`TurnEnergyMeasurement`, model_update и replan. Скрытые
координаты образцов, коэффициенты зон и расписание судьи туда не передаются.

```sh
.venv/bin/python -m unittest discover -s tests -v
docker compose build
docker compose up -d
docker compose exec -T simulation bash docker/entrypoint.sh python3 -m unittest discover -s tests -v
docker compose exec -T simulation bash docker/entrypoint.sh python3 scripts/web_check.py --scenario easy --seed 1 --mode baseline --controls --output /workspace/output/maria-easy-baseline-1.json
docker compose exec -T simulation bash docker/entrypoint.sh python3 scripts/web_check.py --scenario medium --seed 2 --mode adaptive --output /workspace/output/maria-medium-adaptive-2.json
```

Прогоны запускайте **последовательно**: каждый reset пересоздаёт один мир.
`web_check` проверяет реальные команды, физическое положение Gazebo, устойчивые
нули после завершения и публичные данные. Unit/кинематика не заменяют этот тест.
Фактические результаты и ограничения: [validation.md](validation.md).
Регистрация Марии: [experiments/README.md](../experiments/README.md). Реальные Gazebo receipts
сохраняются локально в игнорируемом `experiments/runs/docker`; синтетические
данные регистрируются только с `--test-data`. Не смешивать данные наборов.
