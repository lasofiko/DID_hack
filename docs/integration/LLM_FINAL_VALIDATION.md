## Найдено и исправлено

1. **Поздний ответ после stop возвращал метку LLM.** MissionManager теперь
   сбрасывает источник прерванной цели в Algorithmic. Тест сначала воспроизвёл
   ошибку, затем подтвердил stop, отсутствие движения/collect и единственный
   отрицательный результат INTERRUPTED.
2. **Отказ ML-журнала скрывался переходом на fallback.** Введён отдельный
   `JournalWriteError` с безопасным сообщением. Ошибка открытия/записи журнала
   запрещает запуск через PlannerRuntime; ошибка записи обмена, решения,
   контекста или результата переводит текущую миссию в failed и приводит к stop.
   Это не ошибка провайдера: продолжать без аудита нельзя. Повторная запись того
   же pending-результата после фатального сбоя не предпринимается; требуется
   восстановить журнал и начать новую миссию. Pending не выдаётся за успешно
   записанный результат. Существующий fallback для HTTP/timeout сохранён.
3. **Backend отвергал зарегистрированные гипотезы.** MissionManager теперь
   допускает только null или активный id из реестра текущего ResearchPlanner.
   Добавлено read-only представление id; wire-контракты не менялись. Выдуманные,
   закрытые, сброшенные и некорректные id отклоняются. На синтетическом тесте
   проверены регистрация → выбор → backend result → новое наблюдение → вывод
   «не подтверждена» → передача результата и вывода в следующий prompt.

Гипотезы и выводы не генерируются автоматически. Их формулировки и измеренные
доказательства предоставляет исследовательский модуль. Тест доказывает передачу
состояния и порядок операций, а не физическую истинность гипотезы.

## Ограничения

- Реальные ROS topics/services, сеть между узлами, QoS, TF, colcon, Gazebo и
  физический TurtleBot3 не проверялись. Unit-тесты методов AgentNode используют
  подмены; браузерный UI не запускался.
- Два ответа explore не оценивают статистическую надёжность, реальные collect,
  finish, возврат и влияние задержек на движение. Нельзя заявлять «робот выполнил
  миссию DeepSeek».
- Научные формулировки/измерения/критерии предоставляет исследовательский модуль.
  Новый backend-фильтр id не заменяет экспериментальную методику и не добавляет
  автоматическое создание гипотез в ROS-миссии.
- Fail-stop относится к настроенному ML-журналу. Отдельный agent-journal.jsonl
  сохраняет прежнее поведение с in-memory fallback; этот общий механизм не менялся.
- Stop немедленно запрещает движение, но текущий запрос может завершиться до
  deadline. Shutdown отменяет задачу. Принудительное завершение процесса и
  аппаратное отключение питания отдельно не моделировались.

## Отдельное испытание на стенде / физическом роботе

Выполнять отдельно на подготовленном Linux/ROS-компьютере.

1. Зафиксировать commit, версии ROS/пакетов и конфигурацию; собрать colcon и
   проверить импорт ML/httpx тем Python, который запускает AgentNode. Оставить
   endpoint/model/key на сервере; не публиковать .env/развёрнутый compose config.
   Проверить запись ML-журнала до старта и запрет запуска при её отказе.
2. Для физического робота использовать штатный bringup и реальные драйверы,
   отключить mock judge, проверить TF/odom/scan/battery/clock и координаты карты.
   Текущий web RosRuntime запускает easy.launch с mock_judge=true: этот web-стенд
   сам по себе не является физическим испытанием. Конфигурацию согласует ROS-команда.
3. В ограждённой свободной зоне с оператором у аварийного выключателя сначала
   проверить stop и свежесть сенсоров в algorithmic. Затем короткую LLM-миссию
   с одной достижимой публичной целью и консервативным запасом энергии на возврат.
4. Сопоставить run/session id: UI start → AgentNode → provider exchange →
   candidate/energy validation → source → фактическое исполнение → backend result.
   Проверить collect/finish по реальному сервису, не по тексту reason.
5. Проверить stop во время API, поздний ответ без возобновления движения,
   pause/resume, timeout/fallback, shutdown, reset/новую миссию. Проверить потерю
   свежести и снижение батареи между запросом и исполнением, отказ записи ML-журнала
   до решения и после исполнения: остановка, failed, восстановление новой миссией.
6. До исследовательского действия зарегистрировать гипотезу в текущем planner;
   записать реальные измерения и достаточность данных, только после record_result
   и свежего observe сформулировать вывод. Недостаточные данные → «неопределённо».
7. Сохранить обезличенный отчёт с commit, запросами, задержками и pass/fail каждой
   проверки. При ненулевой скорости после stop, неправильной свежести/энергии или
   отказе обязательного аудита прекратить испытание.
