# ML: планировщик подцелей без обязательной LLM

Реализован `ResearchPlanner`, совместимый с `did_core.ports.Planner`.
Это алгоритмический планировщик с адаптером DeepSeek через API МАИ;
собственной обученной модели и интеграции с роботом пока нет. Проверочный запрос с текущими локальными настройками прошёл: source=llm.

## Запуск сейчас

Из корня, Python 3.12+. Для всего набора тестов установите зависимости: `python -m pip install -e ".[ml]"`. Офлайн-demo не требует сторонних библиотек:

```sh
python scripts/demo_ml.py
python scripts/test_ml.py
```

Demo показывает выбор публичной точки и смену подцели после отказа бэкенда.
Он не имитирует успешную миссию и не использует скрытые образцы.

## Файлы

| Файл | Задача |
|---|---|
| context.py | Достижимые точки, оценки маршрутов, настройки порогов |
| planner.py | Выбор подцели, память, подтверждение результата, fallback |
| validation.py | Проверка наблюдений и строгого JSON |
| provider.py | Интерфейс будущей LLM и построение промпта |
| demo.py | Короткий пример интеграции |

## Что умеет без модели

- Выбирает только из переданных бэкендом достижимых точек.
- Ранжирует точки по информационной ценности, расходу и числу успешных посещений.
- Проверяет бюджет: `(outbound_energy + return_energy) * energy_factor + reserve`.
- Предлагает возврат при исчерпании резерва или отсутствии допустимых целей.
- Предлагает collect только после нескольких разных свежих измерений высокого
  сигнала в небольшой окрестности. Повтор одного sensor timestamp не считается
  новым измерением. После результата collect очищает окно и включает cooldown.
- Временно исключает отклонённые/неудачные точки, ведёт ограниченную память.
- Не предлагает действие при устаревших данных, препятствии впереди или
  невозможном возврате по оценке. Бэкенд должен остановить робот и восстановиться.

Это эвристики, не обученная политика. Рост эффективности на роботе пока не
проверялся. Численные пороги предварительные и требуют калибровки.
Реестр гипотез подключён: hypothesis_id может ссылаться на явно зарегистрированную активную гипотезу. Без реестра используется null.
Модель расхода Марии не заменена: здесь используются готовые оценки от бэкенда.

## Искандеру: как подключить

Для каждой миссии создавать отдельный `ResearchPlanner`.
Обычный `propose(observation, feedback)` сохранён без изменения общего контракта.
Дополнительный PlanningContext нужен, потому что Observation не содержит карту.

```python
from did_ml import Candidate, PlanningContext, ResearchPlanner

planner = ResearchPlanner()

# Наблюдения можно подавать чаще, чем запрашиваются подцели.
planner.observe(observation)
planner.set_context(PlanningContext(
    sim_time=observation['sim_time'],
    pose_x=observation['pose']['x'],
    pose_y=observation['pose']['y'],
    home_energy=home_energy,
    candidates=(Candidate('frontier-1', x, y, outbound_energy, return_energy),),
))
goal = await planner.propose(observation)
# Проверить подцель на АКТУАЛЬНЫХ данных и выполнить её либо отклонить.
planner.record_result(goal, result, sim_time=completion_time)
```

`observation`, координаты, стоимости и `result` в этом фрагменте предоставляет
бэкенд; полностью запускаемый пример — demo.py.

Договорённости:

1. Кандидаты и оценки исходят из публичной карты; недостижимые точки исключаются.
   Возврат оценивается от каждой целевой точки до базы. Координаты — метры map,
   время — секунды симуляции, энергия — единицы батареи, не проценты.
2. Context привязан к точным времени и позиции Observation. Перед новым запросом
   обновлять его. Кандидатов максимум 128; id стабильны между запросами для одной
   и той же исследуемой точки. information_gain — неотрицательный относительный
   приоритет из публичной карты (по умолчанию 1), не расстояние до скрытого образца.
3. К стоимости добавить необходимые затраты движения/поворотов/простоя по
   правилам судьи. energy_factor=1.5 и reserve=8 — предварительные параметры.
   Оценка не гарантирует возврат при неизвестных резких изменениях среды.
4. Единовременно допускается одна неподтверждённая подцель. После неё обязательно
   record_result. Отказ валидатора — Result(success=False, message=причина), затем
   следующий propose с этой причиной в feedback. Result должен соответствовать
   ровно той Subgoal, которую вернул планировщик.
5. Сериализовать observe/set_context/propose/record_result для одного экземпляра.
   Во время ожидания модели обновления нужно держать в агрегаторе бэкенда.
   После await propose ПОВТОРНО проверить свежесть, батарею и карту: состояние
   могло измениться за время API-запроса. Watchdog ROS работает независимо.
6. При UnsafeObservation или PlanningUnavailable остановить исполнение,
   обновить данные/маршрут; не интерпретировать ошибку как разрешение ехать домой.
   При сбросе /clock или новой миссии вызвать reset и передать новый context.
7. collect success означает подтверждение судьи, не обещание планировщика.
   Проверка расстояния до образца остаётся у судьи. Дубликат результата отклоняется.

`planner.history` отдаёт копию ограниченной истории. Для постоянной записи
передайте journal_path в llm_planner: сохраняются входы, промпты, финальные ответы,
задержки и результаты. Реестр гипотез и replay описаны в docs/ml-handoff.md.

## Подключение DeepSeek через МАИ

Реализация — `mai_provider.py`, настройки — `settings.py`, создание и закрытие
клиента — `runtime.py`. По умолчанию выбрана модель `deepseek-v4.1-flash`
из предоставленного списка МАИ.

```sh
python -m pip install -e ".[ml]"
```

Скопировать `.env.example` в `.env` (не перезаписывать существующий файл),
локально заполнить DID_LLM_API_KEY новым ключом. Затем из корня:

```sh
python scripts/check_llm.py
```

Эта команда делает реальный API-запрос с искусственными публичными наблюдениями,
без управления роботом. Результат `source=llm` и код выхода 0 означают, что ответ
модели прошёл проверку. `source=offline_fallback` и код 1 означают, что планировщик
работает, но подключение/ответ модели не прошли проверку. Код 2 — настройки или
зависимости. Ключ и сырые тела ошибок сервера не печатаются.

Скрипт сам читает `.env` из корня, но не заменяет уже заданные переменные окружения.
Backend должен явно загрузить `.env` при старте либо получить окружение от процесса.
Импорт ML-модуля не загружает ключи и не делает сетевых запросов.

### Что требуется подтвердить у МАИ

Документация их шлюза пока недоступна. 8 октября проверочный запрос с локальными настройками успешно вернул валидную подцель (source=llm); это проверка одной ситуации, не оценка качества модели. Маршрут
`https://api-ai.mai.ru/v1/chat/completions` — настраиваемое предположение о
совместимости с Chat Completions, а не проверенный URL. DID_LLM_ENDPOINT задаёт
ПОЛНЫЙ URL, без автоматического добавления /v1. При 404 уточнить маршрут и
идентификатор модели у администратора.

Формат тела/ответа ориентирован на [официальную документацию DeepSeek](https://api-docs.deepseek.com/api/create-chat-completion/).
Поддержка параметров на шлюзе МАИ может отличаться:

- DID_LLM_JSON_MODE=true отправляет response_format=json_object. При его
  неподдержке установить false; строгая локальная проверка JSON остаётся.
- DID_LLM_THINKING=disabled отключает длинное рассуждение, если шлюз понимает
  этот параметр. Если он отклоняется, установить omit. enabled также допустим,
  но может потребовать большего времени и лимита токенов.
- DID_LLM_TIMEOUT=5 — общий лимит одной попытки в секундах.
- DID_LLM_MAX_TOKENS=512 — начальный лимит короткого ответа.

Не увеличивать тайм-аут бездумно: пока модель отвечает, наблюдения устаревают.
Backend обязан повторно проверить их перед исполнением.

### Искандеру: создание планировщика с моделью

```python
from did_ml.runtime import llm_planner

async with llm_planner() as planner:
    planner.set_context(context)
    goal = await planner.propose(observation)
    # Проверить на актуальных данных, выполнить/отклонить, сообщить результат.
    planner.record_result(goal, result, completion_time)
```

Объекты context/observation/result создаёт backend, как в предыдущем разделе.
Держать этот контекстный менеджер на протяжении миссии, а не создавать новый
планировщик для каждой подцели. HTTP-клиент закрывается при выходе.
Без LLM по-прежнему можно создавать `ResearchPlanner()`.

### Обработка ошибок

- 401/403, 404, 429 и другие постоянные ошибки запроса: без повторного вызова
  внутри текущего propose, сразу fallback. После исчерпания попыток действует
  provider_cooldown (по умолчанию 30 секунд реального времени), затем запросы возобновляются.
- Ошибка соединения, тайм-аут, 408/500/502/503/504: до двух попыток суммарно
  (повторы только в ResearchPlanner), затем fallback.
- Некорректный JSON, посторонняя цель или запрещённый collect: отказ валидатора
  и ограниченный повтор, затем fallback.
- Обрезанный ответ (finish_reason не stop), пустой content и ответы с tool calls
  отклоняются. reasoning_content не используется как подцель.
- HTTP-редиректы не выполняются; TLS-проверка не отключается.
- Отмена coroutine пробрасывается, неожиданные программные ошибки не скрываются.

Публичный planner.history содержит безопасные code/status_code, например
`authentication/401`, `rate_limited/429`, `timeout`, без ключей и тела ответа.
Не включать отладочное логирование HTTP-заголовков с Authorization.

## Проверки и оставшиеся задачи

`python scripts/test_ml.py` проверяет алгоритмическую часть и HTTP-адаптер через
httpx.MockTransport, без ключей и расходования квоты. Это не подтверждение
совместимости живого API МАИ — для него предусмотрен check_llm.py.

Остаются у команды: интеграция MissionControl/ROS, локальный поиск градиента,
калибровка и методика научных проб, hard-события, модель расхода и эксперименты
в Gazebo. Готовый ML-модуль не заменяет эти части.


Диагностика отклонений теперь содержит stage и безопасную reason. Ошибка target
исправлена уточнением промпта: только объект {x, y}, без id и метаданных кандидата.
Причина проверки передаётся модели при повторной попытке. Строгая валидация сохранена.
